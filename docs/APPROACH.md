# Approach and design decisions

## Goal

Recreate the supplied Insight.IO dashboard as a working, self-hosted product rather than a static mockup: same information hierarchy, same camera/map swap, plus the real interactions a robot operator would expect.

The reference design is a fixed 16:9 composition. The implementation keeps its visual language while making the layout work from a 390 px phone to a wide desktop.

## Product shape

The dashboard is organized around one always-visible 3D map and a set of glass/white HUD surfaces:

- **Left rail** — brand, primary navigation, profile.
- **Top-left** — mission status, pause control, quick-goal entry.
- **Top-center** — battery, signal, failsafe, system health, and the active view tab.
- **Top-right** — auto/manual mode and initiate mission.
- **Right edge** — emergency stop and manual joystick.
- **Bottom-left** — camera picture-in-picture and camera zoom.
- **Bottom/top hints** — map gestures and loading state.

The camera and map are two real, live views. The swap animates the same components between the main surface and the PiP card, so state is preserved and the PiP is never a fake screenshot.

## Frontend architecture

React owns layout, interaction state, accessibility, and the telemetry snapshot. Three.js owns the map render loop. An imperative `MapEngine` boundary keeps React from re-rendering on every animation frame.

```
SSE frame -> dashboardStore -> MapScene subscriptions -> MapEngine pose/route updates
                          -> HUD components
                          -> CameraFeed / ViewStack
```

- `MapEngine` handles the orthographic camera, OrbitControls, point cloud, walls, zones, labels, furniture, robot, goal ring, route, scan sweep, and responsive framing.
- `useTelemetryStream` owns the SSE connection and reconnect state.
- `useRobotCommands` wraps REST commands with pending/error/toast handling.
- `useDriveController` converts joystick/keyboard input into throttled velocity commands and automatically enables manual mode when needed.
- `useHotkeys` provides `Q`, `V`, `M`, `Space`, and `Esc`.

State is intentionally split into dashboard data, UI state, and transient toasts. Server data is never stored in UI state.

## Map rendering

The map has two inputs:

1. **Generated binary PCD** at `apps/web/public/map/insight-floor.pcd` (97,037 points, fields `x y z rgb intensity`).
2. **Shared floor-plan geometry** in `@insight/shared`, which supplies walls, zones, furniture, goals, and the navigation graph.

The PCD is generated by `npm run generate:pcd` from the facility layout. Keeping the routing graph, zone labels, and point cloud in the same coordinate system avoids the usual mismatch between a pretty floor plan and where the robot actually is.

Key choices:

- **Orthographic top-down camera** for a readable, design-like plan rather than a perspective game camera.
- **Procedural textures** for labels, furniture, the robot, shadows, and the scan sweep. No image atlas or sprite dependency.
- **Zone labels stay upright** relative to the map and are counter-rotated against the floor-plan rotation. They are not flipped 180°.
- **Robot heading** uses `-Math.PI / 2 - heading`; the antenna points along the robot's forward direction. This was visually verified against the goal/route movement.
- **Responsive composition:** wide screens keep the reference's left-weighted camera/map balance. Portrait and PiP containers recenter on the map and adjust the base zoom so the map is not cropped.
- **Pivot compensation** keeps the rotated and horizontally stretched map centered on its world anchor.
- **Progressive loading** reports point-cloud progress and lets the user retry if WebGL or parsing fails.

## Backend and simulation

Fastify exposes a small, typed API and serves the production SPA from the same origin.

`RobotSimulator` is a deterministic 10 Hz simulation:

- Holds mission, pose, velocity, health, route, and goal state.
- Uses the shared A* planner to route between graph nodes.
- Advances pose along the route, turns toward waypoints, drains battery by odometer distance, and completes the mission at the goal.
- Enforces safety rules: manual velocity requires manual mode, an active mission, and no triggered E-stop; E-stop blocks initiate/resume/mode changes until reset.
- Pushes every state change to SSE subscribers and keeps a heartbeat on the stream.

This boundary is deliberate. A production integration would replace `RobotSimulator` with a ROS 2 adapter while keeping the SSE contract and the React UI unchanged.

## Design system

- Tailwind CSS 4 theme tokens for ink, steel, mist, paper, alert red, safety yellow, and live green.
- Inter Variable is self-hosted through `@fontsource-variable/inter`; tabular numbers are used for telemetry.
- Cards share a white/glass surface, hairline borders, soft shadows, and compact uppercase labels.
- Motion is restrained: view swaps use one spring, map transitions interpolate pose, and reduced-motion users get instant state changes.
- Icons come from Lucide; the E-stop bezel and joystick are built from CSS and inline SVG rather than bitmap assets.

## Responsive and accessibility decisions

- The left rail collapses into a bottom navigation bar below `md`.
- HUD blocks move into three rows on phones so the map keeps a usable center area.
- The camera PiP keeps a 3:2 aspect ratio at all sizes.
- All icon-only controls have accessible names; status changes are announced via `aria-live`; modals have labelled titles and Escape handling.
- Focus-visible rings are present on interactive controls.
- `prefers-reduced-motion` removes non-essential transitions.
- Chart-like elements include text values, so color is not the only signal.

## Testing

- **Shared:** graph reachability, route planning/length, point-in-polygon, angle helpers.
- **Server:** simulator lifecycle, E-stop/reset/resume, manual-mode rules, goal changes, SSE subscriptions, API validation and error shapes.
- **Web:** formatting, ETA/distance helpers, goal lookup and zone labels.
- **E2E:** map load, camera/map swap, keyboard shortcut, quick-goal retarget, E-stop reset flow, and mobile viewport overflow.

`npm run verify` is the local quality gate. CI runs lint, typecheck, unit tests, build, and Playwright on Chromium.

## Trade-offs

- **Synthetic telemetry instead of ROS:** keeps the demo installable and deterministic. The socket/state boundary is the upgrade path.
- **Generated point cloud instead of a public dataset:** guarantees the map and navigation agree, and keeps the repository small enough to clone and run.
- **Video instead of a live camera:** the assignment permits a provided video or live feed; the local clip is bundled for offline use.
- **No auth or persistence:** appropriate for a single-operator local dashboard demo; not presented as production security.

## Future work

- ROS 2 web bridge and live `/scan`, `/odom`, `/tf`, and camera topics.
- Real point-cloud streaming with level-of-detail and worker-based parsing.
- Mission history, route editing, and scheduled inspections.
- Authentication, audit log, and multi-robot fleet selection.
